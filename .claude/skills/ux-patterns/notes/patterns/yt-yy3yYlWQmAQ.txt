TITLE: Three UI Secrets — Easing, Feedback, Anticipation
CATEGORY: motion / micro-interaction
URL: https://www.youtube.com/shorts/yy3yYlWQmAQ (YouTube Shorts channel @designmotionhq_yt; not one of the 76 designmotionhq.com/patterns/<slug> pages — Secret 1 (easing) overlaps patterns/easing-curves.txt, but Secrets 2 and 3 package feedback and anticipation as named micro-interaction principles no single 76-page covers)

PROBLEM: "This button feels good" is treated as an accident of taste, when it is actually three separate, nameable decisions (the curve a motion follows, whether an action confirms itself, and whether motion anticipates before it commits) — skip any one and cheap/dead is the result even if colors and layout are right.

RULES:
- SECRET 1 — EASING ("why cheap apps feel off"): linear motion is labeled "Robotic," ease-out is labeled "Alive," shown as two toggled curve plots on the same slider element. Line: "Linear is robotic. Ease out feels alive."
- SECRET 2 — FEEDBACK ("silence = anxiety"): three worked examples — a Subscribe button that visibly pulses on press ("Button Pulse"), a "Changes saved!" toast with a checkmark ("Notification"), and a heart icon confirming instantly on tap ("Instant Feedback"). Separately, a Submit button pair: "No Response" (plain button, "...wait") vs "With Ripple" (ripple effect, resolves to "Confirmed"). Line: "When you tap a button, you need to know it worked."
- SECRET 3 — ANTICIPATION ("Disney knew this in 1937"): a "No Prep" avatar reaction is captioned "Fast, Lifeless"; a "Squash" version (visibly compresses before reacting) is captioned "Satisfying." Line: "A squash before the bounce" — i.e. a brief compress/wind-up beat immediately before the main motion reads as more satisfying than firing the end-state instantly.
- Closing combination shot: a "Payment Details / Send Payment" card demonstrated with all three techniques tagged together (Easing, Anticipation, Feedback) resolving to a green "confirmed" state. Line: "Without them, an app feels dead. With them, it breathes."

DO / DON'T:
- Do: use ease-out (not linear) for any UI element that starts and stops — this is the same rule already recorded in patterns/easing-curves.txt.
- Do: confirm every tap immediately with some signal (pulse, toast, ripple, instant icon state change) — never leave a tap in silence while work happens.
- Do: give a state-confirming action (payment sent, changes saved) a real "resolved" end state (checkmark, "Confirmed" label), not just a spinner that vanishes.
- Do: consider a brief anticipatory beat (a small compress/wind-up) immediately before a confirming animation, when a moment truly needs to read as more satisfying/weighty — the video's example is a "like"/reaction icon, not a whole page.
- Don't: leave an action's result silent — "silence = anxiety" is the video's explicit framing for a tap with no visible response.
- Don't: treat squash-and-bounce as free to apply everywhere; the video's own worked example is a single reaction icon, not routine buttons.

VIDEO ADDS: the two-value "Robotic vs Alive" framing of linear vs ease-out (patterns/easing-curves.txt already has "mechanical and cheap" for linear and settling-into-place for ease-out, so this is a restatement, not new information); the "silence = anxiety" framing for tap feedback and the no-response-vs-ripple Submit-button pair as a concrete before/after; and, genuinely new against all 76 pages, "anticipation" named and sourced to Disney's 1937 squash-and-bounce animation principle, with a Fast/Lifeless vs Satisfying before/after on a reaction icon.

KLADRA: Secret 1 (easing) changes nothing already decided — Kladra's ease-out-as-default conclusion in easing-curves.txt stands. Secret 2 (feedback) reinforces existing discipline: every server-action result in Kladra already needs a toast/inline confirmation ("every state has a word"), and this just adds the framing that a tap with zero visible response reads as broken, not calm — worth keeping in mind for icon-only row actions that currently fire silently. Secret 3 (anticipation/squash-bounce) is the one to flag with CAUTION, not adopt verbatim: Kladra's rule is "nothing lifts or scales on hover" and a restrained, all-business motion budget (100ms hover / 150ms menus / 200ms dialogs and drawers, no number tickers or looping motion) — a squash-compress wind-up on ordinary buttons risks reading as too playful for a cladding company's ops tool, echoing the same caution already raised in patterns/easing-curves.txt about spring/bounce. If anticipation is used at all, it should be narrow and rare (at most a single confirming moment like a toast arriving), never a general button-press treatment, and never anything that reads as a "lift or scale on hover" which is explicitly refused. The continuous "Button Pulse" example must not be read as license for looping/pulsing motion — Kladra's skeletons explicitly do not pulse, and any confirmation pulse used must be a single one-shot beat, not a loop.

PRIORITY: medium — the feedback discipline (never leave a tap silent) is a genuinely useful audit item for icon-only actions, but the headline new idea (anticipation/squash-bounce) is exactly the kind of motion Kladra's existing restraint rules exist to keep out, so its main value is as a named thing to explicitly reject rather than a pattern to adopt.
