TITLE: Z-Index Mastery
CATEGORY: Visual (technical/CSS)
URL: https://designmotionhq.com/patterns/z-index-mastery

PROBLEM: A bigger z-index number doesn't automatically win — it only matters once an element has a positioning context, and even then it's capped by whatever stacking context its parent already lost or won further up the tree, so teams escalate to arbitrary huge numbers instead of fixing the real cause.

RULES:
- z-index needs `position`. Sheet shows the literal broken code: `.card-b { z-index: 9999; }` with no position set — Card B stays behind Card A regardless of the number. Adding `position: relative;` to the same rule (`.card-b { z-index: 9999; position: relative; }`) is what actually makes Card B move on top — captioned "z-index needs position."
- Every stacking context is its own universe: a child element can never climb above its parent's siblings using its own z-index, no matter how large. Sheet demo: Parent A (z-index: 1) vs Parent B (z-index: 2) — Parent B wins. Then a child inside Parent A is given z-index: 9999, but Parent B (and its own children) still visually wins, captioned "9999 inside a context of 1 < 2 outside" — i.e. a huge z-index inside a losing stacking context still loses.
- A z-index arms race (raising numbers to 9999, then 99999) is a symptom, not a fix — the real problem is almost always an unexpected/unintended stacking context created somewhere up the ancestor tree (e.g. by `transform`, `opacity`, `filter`, or `position` + z-index on a wrapper).
- `isolation: isolate` creates a fresh, self-contained stacking context in one line. Sheet shows the exact code `.component { isolation: isolate; }` applied to a component group (Card / Tooltip / Dropdown) so its internal z-index layering can't leak out and fight with the rest of the page — captioned "one line. clean stack" and "new stacking context. no position required" (i.e. `isolation: isolate` does not itself need a `position` value to take effect).
- Debug visually instead of guessing: Chrome DevTools' Layers panel renders the page as a real 3D stack so you can see which element is actually on top. Sheet shows two example layer stacks rendered in 3D perspective: one with Dropdown (z:10) above Card (z:1) above Body, another with Modal (z:20) above Dropdown (z:10) above Card (z:1) above Body — captioned "see every layer. stop guessing."

DO / DON'T:
- Do: give an element `position: relative` (or absolute/fixed/sticky) before expecting its z-index to do anything.
- Do: reach for `isolation: isolate` to contain a component's internal stacking in one line, without needing to also set position.
- Do: open DevTools' Layers panel to inspect the real 3D stack instead of trial-and-error.
- Don't: escalate to `z-index: 9999` (or higher) to force a child above another branch — it can't beat a stacking context its parent already lost.
- Don't: assume a bigger z-index always wins globally — it only ranks siblings within the same stacking context.

None of this exact code or the numeric z-index values are given in the page text.

KLADRA: This is a pure CSS/implementation pattern, not a UX pattern, but it is directly relevant to Kladra's layered surfaces: the record drawer, request dialogs, toasts, dropdowns/comboboxes (shadcn/Radix popovers), and the search palette all stack on top of list/board content and sometimes on top of each other (e.g. a confirm dialog opening from within a drawer, or a toast appearing while a dialog is open). Radix primitives (used via shadcn/ui) generally manage their own portals and stacking, which sidesteps most of this — but any custom-positioned element (a sticky table header, a custom dropdown, an inline confirm) that fights with Radix's portaled layers should use `isolation: isolate` on the component boundary rather than escalating z-index values, and should be debugged with the DevTools Layers panel rather than guessed. RTL has no direct interaction with z-index/stacking-context mechanics — this pattern is direction-agnostic. CONFLICT: none — this is implementation hygiene, not a feature or UI decision, so it doesn't intersect with drag-and-drop/bulk-edit/saved-views/comments/density/motion/gradient rules at all.

PRIORITY: low — valuable as an engineering reference for whoever builds Kladra's overlays (worth keeping in mind to avoid a z-index arms race across drawers/dialogs/toasts/dropdowns), but it's a CSS mechanics lesson rather than a user-facing design pattern, so it doesn't drive any screen redesign on its own.
