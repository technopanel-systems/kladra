TITLE: Live Cursors
CATEGORY: Interaction
URL: https://designmotionhq.com/patterns/live-cursors

PROBLEM: Multiplayer canvases (Figma-style) need to show who else is present and editing in real time, but naively rendering raw server updates or random per-session colors makes cursors jitter and identities unrecognizable, and lets two people silently corrupt the same element.

RULES:
- Interpolate between server ticks: the server streams roughly 10 position updates/sec (10Hz) while the screen redraws at 60fps — interpolate the gap positions client-side so cursors glide continuously instead of visibly jumping/teleporting between the ~10 raw points per second.
- Derive user color from a stable hash of their identity, not a random per-session assignment: formula shown is hash(user_id) → hue, e.g. sarah@acme.co deterministically maps to #14B8A6 every session, with no server coordination needed — so the same person is recognizable by color across logins/days.
- Show presence via an avatar stack with an overflow counter (e.g. three faces + "+5") before anyone has clicked or typed anything — presence is meant to be felt "from the corner of your eye," rendering before a single message or edit happens.
- Lock the element the instant someone selects it, and outline it in that user's color (plus a name badge, e.g. "Sarah is editing") — this prevents two people editing the same shape simultaneously, which would corrupt it; the lock exists to prevent the conflict before it can happen, not to resolve it after.
- Follow mode: clicking another user's avatar binds your viewport to theirs — their pans/zooms drive your screen — functioning as a live design-review substitute for screen-sharing.

DO / DON'T:
- Do: interpolate cursor positions between server ticks so movement reads as smooth 60fps motion.
- Do: derive user color from a stable hash of the ID so it survives across sessions.
- Do: lock an element the instant it's selected and badge it in the editor's color.
- Don't: render cursors at the raw server tick rate — it makes them visibly jump between points.
- Don't: assign colors randomly per session — it resets a person's visual identity every time they rejoin.
- Don't: allow two users to edit the same element at once.

KLADRA: This pattern is built for real-time collaborative canvases (Figma-style multiplayer editing) and largely does not map onto Kladra's architecture — Kladra uses Auth.js credential sessions with one authenticated user acting on a record at a time via server actions, not simultaneous co-editing of the same document by multiple cursors. The core mechanisms (raw-to-60fps interpolation, live cursor rendering, viewport-follow) have no natural home: nobody at a 14-person company is expected to co-edit a quotation or dispatch live with someone else watching their cursor move. Two narrow, weaker echoes are worth naming: (1) stable color-from-identity-hash could inform how Kladra colors people consistently across the app (e.g. Rawan always shown in the same avatar/initial color in the coordinator's queue or team tab, rather than a color reassigned per render) — cheap and useful, independent of any multiplayer feature; (2) the "selection lock" idea (prevent two actors editing the same record at once) is conceptually relevant to a small team where two reps could in theory open the same company record, but Kladra's single-session-per-write-via-server-action model plus its size (14 people) makes silent conflict unlikely, and building a lock/presence layer for it would be over-engineering for the scale. CONFLICT: live multiplayer cursors, presence avatars, and viewport-follow are a live collaborative editing feature — Kladra's standing rules ban comments and have no real-time co-editing surface; building any part of this pattern beyond passive color-consistency would be adding infrastructure (WebSocket-grade real-time presence beyond the single SSE route) not asked for and not fitting the "one SSE route for live updates" constraint, which is meant for status/data updates, not cursor-level presence streaming.

PRIORITY: low — Kladra has no multiplayer canvas and no real-time co-editing surface; only the identity-color-hash idea is worth borrowing, and even that is optional polish, not a gap.
