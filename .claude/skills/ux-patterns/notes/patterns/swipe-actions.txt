TITLE: Swipe Actions
CATEGORY: Interaction
URL: https://designmotionhq.com/patterns/swipe-actions

PROBLEM: Swipe gestures on list rows feel like "one gesture, zero taps" magic when done right, but most implementations skip the physics, direction semantics, and safety net that make swipe safe and discoverable, turning it into a data-loss bug and a hidden feature nobody finds.

RULES:
- Swipe actions are invisible UI: without an affordance hint (a brief peek of the action row on first load, or an onboarding nudge), most users never discover them exist at all. Sheet shows a "NEW USER" inbox where the first row's action buttons peek out automatically on first launch, captioned "invisible until you teach it" / "teach once, then never again" — with an explicit two-launch comparison: "Launch 1: peek hint" fires the teaching animation, "Launch 2: nothing — learned" skips it once the user has seen it.
- Threshold design needs two distinct trip-wires, not one: a reveal threshold (a short partial pull just exposes the action buttons, firing nothing) and a separate, further commit threshold (releasing past that line actually fires the action). Sheet's slider diagram marks REVEAL and COMMIT as two separate points along the swipe distance, captioned "reveal is a menu, commit is a decision."
- Use rubber-band physics so the row visibly resists past a point: a graph of "row displacement vs. finger travel" is linear/1:1 up to the reveal point, then flattens into a resistant "rubber-band zone" so the user feels friction before commit; past the commit threshold the resistance releases (paired with a haptic tick on mobile) and the row snaps to the fully-revealed/committed state. Caption: "resistance is feedback."
- Direction carries fixed semantics app-wide: swipe right reveals safe, reversible actions (archive, mark as read — "reversible in one tap"); swipe left reveals destructive/costly actions (delete, unsubscribe). Sheet explicitly warns against swapping this convention — a "sides swapped" frame is marked with a warning icon and captioned "muscle memory has no undo," meaning once a user has built muscle memory for right=safe/left=destructive, reversing it in one screen but not another turns a habitual gesture into an accidental destructive action.
- Destructive swipes need friction, not a modal confirm dialog: a full swipe that instantly deletes is a data-loss bug waiting to happen, but the fix shown is not a blocking "Are you sure?" dialog — it's committing the action immediately behind a visible undo window (a red full-width bar with a circular countdown/undo control) that can be reversed for a few seconds after. Caption: "no dialog, just a net" / "delete fast, forgive faster."
- Color-code consistently by consequence: neutral actions (archive) on surface/brand tones, destructive actions (delete) on red — and keep that color-to-action mapping identical across every list in the app.
- Never make swipe the only path to an action: every swipe action needs a visible fallback (a long-press menu, or a button in the row/detail view) so the action stays discoverable and accessible to users who never swipe.

DO / DON'T:
- Do: pair each swipe action with an undo window, and keep left/right semantics consistent app-wide.
- Do: give first-time users a one-time peek/teaching animation, then never repeat it.
- Don't: hide more than two actions per side — beyond that, users can't build muscle memory.
- Don't: swap which side (left/right) maps to safe vs. destructive between different lists in the same app.
- Don't: let a full swipe commit a destructive action with no undo path.

VIDEO ADDS: The two-trip-wire threshold mechanic (separate reveal vs. commit points on the drag distance) with an actual displacement-vs-finger-travel graph showing the rubber-band flattening and the haptic tick at commit; the explicit right=safe/left=destructive direction convention shown as two real inbox rows plus a "sides swapped" anti-pattern warning; the exact teach-once discoverability mechanic (peek animation on launch 1, nothing on launch 2); and the "no dialog, just a net" undo-bar mechanic shown as an actual committed-but-reversible delete state with a countdown control — none of the trip-wire/rubber-band mechanics, the direction-swap warning, or the undo-bar visual are in the page text.

KLADRA: This entire pattern is about swipe-to-reveal row actions on touch — directly relevant to Kladra's phone layout (375px, reps in the field) for list rows in companies/projects/quotations/dispatches. CONFLICT: Kladra's standing decisions list "no drag-and-drop" explicitly, and the sibling hover-trap pattern already flagged that swipe-to-reveal is not part of Kladra's established toolkit ("the safer home for Kladra is 'in the card' [always-visible actions] or a menu, not swipe or a bottom sheet"). Swipe actions are a gesture-only interaction in the same family as drag-and-drop (a continuous pointer/touch gesture driving direct manipulation of a row), so adopting this pattern would introduce a new gesture-based interaction model Kladra has so far avoided — flagging this plainly as a likely conflict with the spirit of "no drag-and-drop," not resolving it. Separately, the "no dialog, just a net" undo-bar approach for destructive actions (commit immediately, offer a timed undo) is a reusable idea independent of swipe — it could inform how Kladra confirms a destructive action generally (e.g. removing a line item or archiving a record) without a modal, though Kladra currently has no stated stance on toast-based undo vs. confirm dialogs for destructive actions, so this would need founder confirmation before use even outside the swipe context.

PRIORITY: low — given the standing "no drag-and-drop"-adjacent decision and the sibling hover-trap agent's finding that swipe is deliberately not part of Kladra's toolkit, the swipe-specific mechanics here (thresholds, rubber-band physics, direction semantics) are not actionable without the founder first deciding to introduce gesture-based row actions; the undo-window idea for destructive actions is worth surfacing separately as a general interaction question, not tied to swipe.
