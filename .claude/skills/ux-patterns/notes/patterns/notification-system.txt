TITLE: Notification System
CATEGORY: Feedback
URL: https://designmotionhq.com/patterns/notification-system

PROBLEM: Notifications are treated as one interchangeable component, so teams route every event to whichever surface is easiest to reach for — usually the loudest one — which trains users to tune out all of them.

RULES:
- A notification is a system of four surfaces, not one component: toast, banner, modal, and badge — the same underlying content can be delivered at four different volumes.
- The trigger's severity picks the surface, not preference: a low-priority event ("new message") fits a toast; a degraded-service warning fits a banner; a blocking failure ("card declined") fits a modal; a passive count ("3 unread comments") fits a badge.
- Persistence is part of the contract per surface: toasts auto-dismiss after a few seconds (and should offer an undo action before they do); banners stay until manually cleared/dismissed; modals block until the user explicitly acts; badges sit quietly, showing a count, until the underlying thing is resolved.
- Stack behavior separates good design from broken design: multiple toasts can stack and "breathe" (readable, non-overlapping); multiple modals stacked on top of each other become a trainwreck — blocking dialogs must never queue on top of one another.
- Over-escalating backfires: routing everything to the loudest surface (modal) trains users to ignore all surfaces, producing zero attention rather than more.

DO / DON'T:
- Do: map each notification's severity to the surface that matches it — toast, banner, modal, or badge.
- Do: let toasts auto-dismiss with an undo affordance, and reserve modals for actions that genuinely must block.
- Do: stack low-priority notifications so they breathe instead of piling up on screen.
- Don't: route every alert to the most intrusive surface — over-escalation trains users to ignore all of them.
- Don't: queue multiple modals on top of each other; stacked blocking dialogs are a trainwreck.
- Don't: use a blocking modal for a low-severity, purely informational message.

KLADRA: This maps directly onto CLAUDE.md's own explicit surface list ("toasts and notifications") and Kladra's single SSE route for live updates, which is the natural trigger source for banners/toasts/badges. Concrete application: (1) toasts for low-priority, transient confirmations (a save succeeded, a status changed) — auto-dismiss with an undo affordance where the action is reversible, echoing the inline-editing pattern's optimistic-save/rollback logic; (2) a banner for a degraded/ongoing condition worth surfacing until acknowledged (e.g. "SSE connection lost, reconnecting" or a sync issue) — manually dismissed, not timed; (3) a modal reserved for genuinely blocking failures that need an explicit decision (e.g. a destructive action's confirm, or a failed write that needs the user to choose retry vs. discard) — matches the modal-hierarchy pattern's "does it block?" gate; (4) a badge for passive counts — e.g. an unread/pending count on the coordinator's queue or a notifications icon in the shell — a static number is fine and does NOT conflict with Kladra's "no number tickers" rule, since that rule bans animated incrementing counters, not a plain badge count that updates in place; worth confirming the badge update itself doesn't animate/tick when it changes. The "never stack modals" rule is a hard constraint worth enforcing given Kladra's request dialogs and destructive confirms — a second blocking action should queue after the first resolves, never render on top of it. No conflict with standing Kladra rules otherwise; notifications are explicitly named as a first-class Kladra surface, and stacking toasts (not modals) is compatible with "no refresh buttons" since a toast can carry its own undo instead of prompting a manual refresh.

PRIORITY: high — Kladra already has toasts/notifications as a named surface and a live-update SSE route feeding them; getting the severity-to-surface mapping and the never-stack-modals rule right prevents both under-alerting (a failed write shown only as a quiet badge) and over-alerting (every save producing a blocking modal) across a small team that will notice either failure mode quickly.
