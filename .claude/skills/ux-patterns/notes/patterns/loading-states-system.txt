TITLE: Loading States System
CATEGORY: Feedback
URL: https://designmotionhq.com/patterns/loading-states-system

PROBLEM: Reaching for one default loading indicator (usually a skeleton) for every wait, regardless of what's actually known about that wait's shape, duration or progress, is a lazy pattern that either misleads the user or flickers distractingly on fast responses.

RULES:
- Loading is a system of five choices picked by what you know about the wait, not a single default:
  1. Skeleton — use when you know the content's shape (cards, lists, articles) AND the wait exceeds ~300ms; it previews the layout about to load, setting the right expectation.
  2. Spinner — use for short waits of unknown duration, under ~3s (e.g. a button save, a small fetch). Never stretch a spinner across a full-page load — an endless spinner with no context reads as frozen, not loading.
  3. Progress bar — use for waits over ~3s where the percentage is knowable (uploads, installs, exports); pair the bar with real metadata (time remaining, speed) so the number earns trust rather than looking fake.
  4. Optimistic UI — the "pro move" for reversible actions (likes, saves, bookmarks): update the interface instantly, reconcile with the server in the background, and only surface an error if the sync actually fails.
  5. Show nothing — under ~300ms, show no loading indicator at all. A brief flash of a loading state at that speed reads to the eye as a glitch, not as feedback, and feels more broken than a slight delay would.
- Match granularity matters: known shape → skeleton; known percentage → progress bar; short unknown wait → spinner; reversible action → optimistic; sub-300ms → nothing.

DO / DON'T:
- Do: pick the pattern from what you know — known shape → skeleton, known percentage → progress, short unknown wait → spinner.
- Do: apply the response instantly for reversible actions, sync in the background, and roll back only on failure.
- Do: let sub-300ms responses land with no loading indicator at all.
- Don't: reach for a skeleton on every fetch regardless of content shape or duration.
- Don't: cover a whole page with a spinner for a long or open-ended load.
- Don't: flash any loading state for a response that resolves in under 300ms.

KLADRA: This maps directly onto CLAUDE.md's own standing motion rules and validates several of them: Kladra already mandates "no number tickers or looping motion (skeletons do not pulse)" — this pattern's own skeleton example is a static placeholder with no pulse shown anywhere in the video, so the two are compatible, not in tension; Kladra's skeletons can use this pattern's "known shape → skeleton, >300ms" rule as-is (e.g. companies/projects/quotations/dispatches list and board skeletons while data loads). Direct applications: (1) the coordinator's queue and record drawers loading from the server should use skeletons matching their real layout only past ~300ms, never a generic spinner; (2) inline saves (editing a field, changing a status) should use the spinner-in-button pattern ("Saving…" → "Saved") for short unknown-duration writes, which fits Kladra's "every state has a word" rule since "Saving…"/"Saved" are literal words, not color-only cues; (3) any file export or multi-step server action taking >3s (e.g. a large report/backup) should show a real progress bar with time-remaining, not an indefinite spinner; (4) fast interactions (toggling a status, opening a drawer that's already cached) under 300ms should show nothing, consistent with Kladra's "no refresh buttons" ethos of not manufacturing UI busywork. Optimistic UI pairs well with Kladra's single SSE route: apply instantly, reconcile via SSE, roll back with a toast + reason on failure — same shape as the inline-editing pattern's optimistic-save rule. No conflict with standing Kladra decisions; this pattern actively reinforces the "skeletons do not pulse" and "every state has a word" rules already in place.

PRIORITY: high — loading state choice touches nearly every screen in Kladra (lists, boards, drawers, forms, exports) and the five-way decision tree is a concrete, low-cost rule to apply consistently across the whole app during the re-audit, directly reinforcing rules already written into CLAUDE.md.
