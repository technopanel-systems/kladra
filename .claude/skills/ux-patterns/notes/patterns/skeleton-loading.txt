TITLE: Skeleton Loading
CATEGORY: Feedback
URL: https://designmotionhq.com/patterns/skeleton-loading

PROBLEM: A spinner tells the user "something is happening" but gives zero information about what or how long, and that uncertainty is what makes a wait feel slow — a skeleton that previews the incoming layout reads faster even at the same real duration.

RULES:
- Skeleton screens preview the shape of incoming content (avatar circle, text bars, image block) so the brain starts parsing layout before data arrives, rather than staring at an abstract spinner. Sheet's side-by-side: a spinner card shows generic placeholder copy while loading a social post; a skeleton card shows shimmering bars already shaped like the name line and body text that will appear.
- "The Brain — Prediction Machine" framing: a spinner reads as WAITING and is captioned with a red "STRESS" bar; a skeleton reads as PREDICTING and is captioned with a green "ENGAGEMENT" bar, with the word "ANTICIPATION" as the payoff — the claim is that seeing the shape of what's coming lowers perceived stress versus an undifferentiated spinner.
- The shimmer sweep matters: a static (non-animated) skeleton reads as "broken"; an animated shimmer reads as "in progress."
- Shimmer direction should follow natural reading flow: sheet explicitly compares a shimmer sweeping left-to-right marked "→ NATURAL ✓" against one sweeping right-to-left marked "← REVERSED ✗" — i.e. the sweep direction is expected to track the text reading direction of the locale, not be hardcoded left-to-right.
- Match the skeleton shape to the actual content dimensions/layout — content-aware, not generic. Sheet contrasts a "GENERIC" skeleton tagged "LAZY" (uniform grey bars unrelated to the real layout) against a "CONTENT-AWARE" skeleton tagged "SMART" that mirrors the real card exactly: avatar circle, name line, two text lines, and a chart-shaped block sized like the actual chart that will render. A skeleton that jumps to a different layout once real content loads is worse than a spinner.
- For actions the user just performed (posting, liking, commenting), skip loading states entirely: render the result optimistically and reconcile with the server in the background. Sheet shows a comment posting instantly with its like/comment/share counts visible, then two branching timelines — SUCCESS (click → show result → server confirms, count stays) and FAILURE (click → show result → server fails, count/state reverts) — captioned "the beautiful lie."
- Timing rule from the page text: keep skeletons under roughly 2 seconds before showing at least partial real content.

DO / DON'T:
- Do: shape skeletons to mirror the final layout, animate the shimmer, and keep the skeleton state under about 2 seconds before showing partial real content.
- Don't: use a skeleton for sub-300ms loads (a flash of skeleton is just noise).
- Don't: mix spinners and skeletons within the same view.

VIDEO ADDS: The reading-direction rule for shimmer sweep direction (natural left-to-right vs. reversed, marked correct/incorrect) — directly relevant to Arabic RTL and not mentioned in the page text at all; the "generic/lazy vs. content-aware/smart" skeleton comparison shown as two real card mockups (one with a mismatched shape, one with an exact chart/avatar/text match); and the optimistic-UI success/failure branching timeline showing exactly what reconciliation looks like when the server later disagrees with the optimistic render (count/state rollback) — none of this is in the page text.

KLADRA: Applies to any list or drawer that loads data — companies/projects/quotations/dispatches lists and boards, record drawers, the coordinator's queue, dashboards. Two points are especially load-bearing for Kladra: (1) the RTL shimmer-direction rule is a genuine, currently-undocumented detail — if skeletons in Kladra were ever animated, the sweep would need to run right-to-left in the Arabic locale, mirrored via logical CSS, matching Kladra's existing "logical CSS for RTL" rule; (2) content-aware skeleton shapes (matching the real row/card layout, including chart-shaped placeholders for dashboard KPI cards) is directly reusable and conflict-free. CONFLICT: Kladra's standing rule is explicit — "no number tickers or looping motion (skeletons do not pulse)" — this pattern's central recommendation is an animated shimmer sweep, justified here as reducing perceived stress and signaling "in progress" rather than "broken." This directly conflicts with Kladra's static-skeleton decision; flagging plainly rather than resolving it. The optimistic-UI rule (skip loading state for user-initiated actions, render immediately, reconcile after) does not conflict with any standing decision and is a good practice for Kladra's server-action writes (e.g. a quick status change or note add) — though it may interact with the "no refresh buttons" and SSE-live-update rule in ways worth checking against how Kladra's single SSE route already pushes updates.

PRIORITY: medium — the content-aware skeleton shaping and the RTL shimmer-direction detail are cheap, useful, and conflict-free; the core animated-shimmer recommendation is blocked by Kladra's static-skeleton rule and should not be adopted without the founder explicitly revisiting that decision.
