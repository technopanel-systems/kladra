CROSS-CUTTING PRINCIPLES ACROSS THESE 38 PATTERNS

1. Every state needs a word, not just a color or a position shift. This recurs directly in color-accessibility, filter-chips, form-field-states, data-table, disabled-buttons, dropdown-design, and focus-states — it is the numeric/behavioral backing for a rule Kladra has already adopted, not a new idea.

2. Feedback must be instant (~400ms, doherty-threshold) and honest, never faked. Autosave-ux, file-upload-ux, error-states, behind-the-button, and filter-chips all independently arrive at the same rule: show real percentages/counts/status, update them on the same frame as the triggering action, and never let a status indicator claim success that didn't happen.

3. Motion needs both a duration and a curve, chosen on purpose and reused everywhere. Animation-timing, easing-curves, card-hover-anatomy, and accordion-disclosure each show that the same distance/duration reads completely differently depending on the easing function — Kladra's existing 100ms/150-250ms rules need a matching curve decision (ease-out for entrances, spring reserved for rare emphasis) recorded once, not re-guessed per component.

4. Every dead end needs an exit. Error-states, empty-states, destructive-actions (a cancellable grace period over a confirm modal), drag-and-drop's undo toast, and file-upload's inline retry all reject the pattern of a terminal failure state with no way forward — retry, undo, or a clear next action is mandatory, not optional.

5. Never trust the client for anything that matters, and never let the client fake success. Behind-the-button, autosave-ux (offline queue, conflict handling), and form-validation-timing all converge on: validate on the client for speed, but the server (or explicit confirmation) is the only source of truth, especially for money and shared records.

6. "It's a system, not a control" is the recurring reframe. Data-table, command-palette, error-states, context-menu, empty-states, dropdown-design, destructive-actions, and filter-chips are all explicitly framed by the source as a small system of states/behaviors rather than one component — the practical implication for Kladra is to build each of these once as a shared, fully-specified component rather than re-deciding sort/validation/error-surface/empty-copy per screen.

7. Foundational token work (color, spacing, motion, radius, gradients) pays off once at the DESIGN.md level. Design-tokens, design-system-kit, dark-mode, border-radius, grid-system, gradient-design, golden-ratio, and depth-layers are all really the same instruction in different clothes: name the scale, apply it everywhere, and stop re-deciding pixel/hue/duration values screen by screen.

8. A recurring minority of patterns collide directly with Kladra's standing bans — worth one consolidated conflict review rather than resolving piecemeal: drag-and-drop (banned outright, only its undo-toast idea survives), bulk-actions (bulk edit banned, only undo-over-confirm survives), data-table's density toggle (banned, sort/alignment/freeze survive), filter-chips/date-pickers brushing against "no saved views" (fixed quick-ranges and chip filters are not user-saved views — state that distinction if raised), gradient-design's mesh/ambient-glow/gradient-text uses brushing the two-gradient cap (only the hue/direction/contrast craft rules for the two allowed gradients survive), and doherty-threshold's own looping-spinner and percent-ticker demo clips brushing "no number tickers or looping motion" (the underlying visible-feedback-under-400ms idea survives in static/worded form). None of these need the underlying pattern rejected wholesale — each has a non-conflicting subset worth keeping, as noted per-file above.
