TITLE: Modal Hierarchy
CATEGORY: Interaction
URL: https://designmotionhq.com/patterns/modal-hierarchy

PROBLEM: Most apps default to a full-screen blocking modal for every overlay need, adding interruption and friction to routine, non-blocking actions that a lighter overlay (sheet, drawer, popover) would handle better.

RULES:
- Start every overlay decision with one question: does it block the user? If yes → modal. If no → choose by context: sheet, popover, or drawer.
- Modal: takes over the screen with a full scrim, centers a single decision. Reserve it strictly for critical or destructive choices that must be answered before anything else continues (example given: "Delete account?").
- Bottom sheet: the mobile-first default overlay — slides up from the bottom edge, supports a drag handle and snap points, and keeps the screen behind it partly visible so the user doesn't lose context (unlike a modal's full scrim).
- Drawer: an edge-anchored panel, typically used for navigation — slides in from the side, dims only the area it covers, and leaves the rest of the app alive/interactive behind it.
- Popover: anchors to the exact element that triggered it, stays small and contextual (~200px), used for lightweight menus and quick actions — never for a blocking flow.
- Match weight to intent: modals interrupt by design; popovers and sheets are meant to stay non-blocking. Reaching for a modal when a popover would do adds unnecessary friction to a routine action.

DO / DON'T:
- Do: ask "does this block the user?" before picking any overlay type.
- Do: reserve modals for critical or destructive decisions that demand a response.
- Do: anchor popovers to their trigger element and keep them small and contextual.
- Don't: reach for a modal when a lightweight sheet or popover would do the job.
- Don't: use a full-screen scrim for a routine, non-blocking action.
- Don't: bury navigation inside a blocking overlay — use an edge drawer instead.

KLADRA: Kladra already uses modals/dialogs and drawers per CLAUDE.md's own vocabulary ("modal-hierarchy... 150-250ms for dialogs/drawers," record drawers, request dialogs). This pattern gives a clean rule to apply directly: (1) the request dialogs (create/edit quotation, dispatch, project) and any destructive confirm (delete a company, cancel a dispatch) should be true blocking modals — matches CLAUDE.md's own 150-250ms dialog motion budget; (2) record drawers (company/project/quotation/dispatch detail) are the edge-anchored "drawer" type — already Kladra's pattern, and correctly non-blocking since the list behind stays visible; (3) any small contextual menu (status change dropdown, a filter chip's option list, an overflow "..." menu in a list row) should be a popover, anchored and small, not a bespoke dialog — this is where a common over-modaling mistake would show up; (4) the "bottom sheet" mobile-first overlay is the piece Kladra doesn't yet clearly have named — worth deciding explicitly whether the 375px phone layout for reps in the field should turn drawers/filters into bottom sheets on narrow screens, since a side drawer is often awkward at 375px width. The decision tree ("does it block?" then "mobile or contextual?") is a good one-question gate to apply screen-by-screen during the re-audit. No conflict with standing Kladra rules — modals/drawers/popovers are all already part of Kladra's toolkit (shadcn/Radix dialog, sheet, popover primitives); this pattern doesn't touch drag-and-drop, bulk edit, saved views, or comments.

PRIORITY: high — overlay choice (modal vs drawer vs popover) is used on nearly every Kladra screen (every create/edit flow, every record view, every status change), and picking the wrong weight for a given action is a common, easy-to-fix mistake worth checking systematically during the front-end re-audit.
