TITLE: Password Field UX
CATEGORY: Forms
URL: https://designmotionhq.com/patterns/password-field-ux

PROBLEM: A password that satisfies every listed rule (a capital letter, a symbol, eight characters) can still be trivially weak, while the UI only tells the user that after they've already failed to submit.

RULES:
- Strength is entropy, not a checkbox tally — a longer passphrase beats a mandatory symbol every time. Sheet contrasts `P@ssw0rd!` (complex & short: 8+ chars, symbol, number tags, crack time "2 hours", 11 bits of entropy) against `wrong-mango-battery-sky` (simple & long: 23 characters, zero symbols, far longer crack time, 21 bits of entropy) — the "complex" one is weaker.
- Show the requirements checklist live as the user types and tick each rule green before submit — never reveal rules only after a failed attempt. Sheet compares "rules after submit" (password typed, then red errors appear: "Must contain an uppercase letter," "Must contain a number," "Must contain a symbol") against "checklist while typing" (rules listed beside the field, each ticking green live: 1 uppercase, 8+ characters, 1 number, 1 symbol).
- A live strength meter coaches in real time — a growing bar says "almost" — while post-submit errors only punish after the fact. Sheet shows the meter growing from a short red "Weak" bar (input "tan") to a full green "Strong" bar (input "tango-river-lamp") with tags like "4+ chars," "two words," "a number."
- Add an eye toggle to unmask the field; masked dots cause silent typos users can't catch.
- Never block paste — password managers fill longer, stronger passwords than anyone types by hand. Sheet shows a "Block paste" option struck through/rejected in favor of "Allow paste," with a pasted 22-character unique password (`horse-velvet-anchor-42`) landing cleanly in the field.
- The strongest pattern is a one-tap generated password, built into iOS/Android/every modern browser: "Use suggested password" auto-fills a random strong value (e.g. `kV9#mQ2-xT8&wNp4`), tagged "Generated," "Unique," "Saved to keychain" — no typing at all.

DO / DON'T:
- Do: surface a live checklist and strength meter that update on every keystroke.
- Do: offer a visibility toggle plus a one-tap generated password.
- Do: allow paste so password managers can fill strong credentials.
- Don't: hide the rules until after submit, then punish with red errors.
- Don't: treat a capital-and-symbol checkbox as proof of real strength.
- Don't: block paste or force users to retype long passwords manually.

VIDEO ADDS: A direct numeric entropy comparison (11 bits / "2 hours to crack" for the complex-short password vs 21 bits / a much longer crack time for the simple-long one) that the text only gestures at; literal before/after error-copy for the "rules after submit" failure state (three specific red requirement strings); a live-typing strength-meter sequence with real example strings (`tan` → weak/red, `tango-river-lamp` → strong/green, `Summer24!` → "Fair") and the coaching tag chips shown next to the bar; a rendered browser-native "Use suggested password" flow end to end (suggestion shown, accepted, field fills, strength jumps to Strong, tags "Generated / Unique / Saved to keychain" appear); and the closing line "Managers type stronger passwords than humans," tying the whole pattern to password-manager compatibility.

KLADRA: Applies to Kladra's Auth.js credentials sign-in and any admin/manager password-set or reset screen (Jerom as admin, Abdulrahman as manager likely have account settings). Since Kladra uses database sessions with credentials auth, the account-creation or password-change form should show a live checklist and strength meter rather than post-submit errors, allow paste (so a manager's password manager works), and never block a generated/pasted long passphrase. Given Technopanel is a 14-person company, a generated-password affordance is a reasonable low-effort win for admin-created accounts. No conflict with standing decisions — this is a forms/auth pattern, orthogonal to drag-and-drop, bulk edit, saved views, comments, and density; motion for the strength-bar fill should stay within the 100ms interaction budget (a growing bar on keystroke, not a looping animation).

PRIORITY: medium — Kladra almost certainly has a password field somewhere (account creation/reset for Faisal, Rawan, Abdulrahman, Jerom), and live-checklist-plus-meter is a well-understood, cheap-to-implement upgrade over post-submit validation, but it touches only one or two screens, not core CRM surfaces.
